# Pass1 基礎調査 エージェント型検索 基本設計（ドラフト）

作成日: 2026-08-15
ステータス: **ドラフト・未実装**。[docs/api-cost.md](api-cost.md) で試算していた「手動オーケストレーション」（`lib/researchOrchestrator.ts`、候補生成→個別グラウンディング→深掘りの3段階を固定回数で回す設計）を置き換える。

## 1. 背景・課題

`lib/researchOrchestrator.ts` は、Web検索1回につき実質1クエリしか検索しない `Chat Completions API` の `web_search_options` を前提に、検索回数（何を・何回調べるか）を**人間が事前に固定設計**する方式だった。この方式には構造的な限界がある。

- 検索回数を「良さそうな数」まで人力で継ぎ足すたびに、その数字が正しい根拠を持たない（5→8→11→14→17回、と際限なく増やせてしまう）。
- 候補を並列で数十件投げるとタイムアウト・接続エラーで破綻する（実測: 30並列でタイムアウト）。
- 「もっと深掘りできないか」を試すたびに新しい価値が見つかり続けるが、これは天井を検出できているのではなく、**ほぼどんな追加クエリでも何かしら価値のある情報が見つかる**ことの裏返りにすぎない。

一方、`Responses API` の `web_search` ツール（`gpt-5.1`）を1回呼び出すだけで、上記の17回オーケストレーションより包括的な結果が実測で得られた（[docs/api-cost.md](api-cost.md) 参照）。これはChatGPT等が使う「モデル自身が必要な分だけ反復的に検索するエージェント型」の仕組みであり、検索回数の設計をアプリ側の人力から**モデル自身の判断**へ移す。

## 2. 新設計の要点

1. **検索回数を固定パイプラインで設計しない。** `Responses API` + `web_search` ツールに一任し、1回のAPI呼び出し内で何回検索するかはモデルに委ねる。
2. **「深掘り」は固定段階ではなく、会話の継続（マルチターン）で実現する。** 人間が調査を深める際の「もっと詳しく」「この観点は？」という継続確認と同じ形を踏襲する。
3. **深掘りの「やめどき」は固定回数ではなく、品質メトリクスの伸びが鈍化した点で決める**（4章）。

## 3. アーキテクチャ

### 3.1 検索担当（Pass1相当）

- `client.responses.create({ model: "openai/gpt-5.1", tools: [{ type: "web_search" }], ... })` を使用。
- 初回ターン: `research_facts.md` 相当の方針（ベースライン事実＋代替ルート探索、`goal.type`別の着眼点）をそのまま `instructions` として渡し、`input` にユーザー入力を渡す。1回で足りない場合、モデルが内部で複数回 `web_search_call` を実行する（実測: 1〜2回/ターン、詳細は5章）。
- 追加ターン（深掘り）: `previous_response_id` で会話を継続し、「もっと深掘りして」に相当する具体的な追加指示（後述4章の停止判定に応じて動的に、または固定の追加観点プロンプトで）を送る。

### 3.2 統合先（Pass2相当）との関係 ― 検証済み・2段階構成を維持

現行は「Pass1(検索・軽量facts) → Pass2(検索なし・ResearchResultフルJSON生成)」の2段階。`Responses API` の `web_search` ツールと `text.format`（構造化出力）を併用すれば1本の呼び出しに統合できないか実際に検証した。

**検証結果（2026-08-15、`gpt-5.1`）**: `web_search` ツールと `researchResultSchema` の `text.format` を同時に指定し、`research_system.md` の方針でフルJSONを直接生成させたところ、

- **所要時間 2073秒（約34.5分）**。Vercelの `maxDuration=120` は言うに及ばず、同期リクエストとしておよそ実用に耐えない。
- **`web_search_call` 回数は0回**。スキーマ検証は通り `sources` も3件生成されたが、実際には一切検索せず一般知識だけで出典らしきものを作った可能性が高い（＝グラウンディングの意味がない）。大きな構造化出力スキーマを同時に満たそうとすると、モデルが検索よりスキーマ充足を優先してしまう懸念がある。

→ **結論: 統合しない。2段階構成を維持する。** 検索担当（新設計）の出力は引き続き軽量な `facts`/`sources`（`FactFindingResponse` 相当）とし、`prompts/research_system.md` によるPass2（検索なし、既存のまま）でJSONを組み立てる。

### 3.3 `lib/researchOrchestrator.ts` の扱い

新方式に置き換わり次第、3段階の固定オーケストレーション（候補生成／個別グラウンディング／深掘り）とそれに付随する `prompts/research_candidates.md` / `prompts/research_grounding.md` / `types/researchCandidates.ts` は削除する。`prompts/research_facts.md` の内容（`goal.type`別の着眼点等）は、新方式の初回ターンの `instructions` に引き継ぐ。

## 4. 深掘りの「やめどき」をどう決めるか

固定回数を人力で決め打ちしないための、暫定の停止判定方針:

- **測定対象を中間生成物（facts件数等）ではなく最終成果物にする。** `ResearchResult` における「根拠（sourceIndex）が実際に使われた箇所の数」「distinctな`sources`件数」を品質の代理指標とする（`docs/api-cost.md` の予算比較テストで使った指標を流用）。
- **追加ターンごとに指標を測り、伸びが頭打ちになったら止める。** 例えば直前ターンに対する指標の増分が閾値（要チューニング、暫定案: 前ターン比+10%未満）を下回ったら深掘りを終了する。
- **上限ターン数はコスト・レイテンシの安全弁として設定する**（品質根拠ではなくコスト制約としての上限、と明確に位置づける）。`maxDuration=120`（Vercel）に収まる範囲で、暫定上限は4〜6ターン程度から実測して調整する。
- この「伸びの鈍化で止める」ロジック自体をアプリ側に実装するか、モデルに「十分調べ終えたと判断したら止めてよい」という自己判断を委ねるかは、5章の追加検証で決める。
