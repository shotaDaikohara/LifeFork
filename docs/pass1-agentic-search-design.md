# Pass1 基礎調査 エージェント型検索 基本設計

作成日: 2026-08-15
ステータス: **基本アーキテクチャは実装済み**（`lib/researchAgent.ts`、`mode: "normal"`、非同期ポーリング方式）。旧・手動オーケストレーション（`lib/researchOrchestrator.ts`、候補生成→個別グラウンディング→深掘りの3段階を固定回数で回す設計）を置き換えた。旧関連ファイル（`prompts/research_candidates.md` / `prompts/research_grounding.md` / `types/researchCandidates.ts`）は削除済み。
**ただし「実クエリ数100回相当の深さを自然に達成する」という目標については、9章で説明する停滞バグが見つかったため未達。9章の対策（スタール検出）は設計のみで未実装。**

## 1. 背景・課題

`lib/researchOrchestrator.ts` は、Web検索1回につき実質1クエリしか検索しない `Chat Completions API` の `web_search_options` を前提に、検索回数（何を・何回調べるか）を**人間が事前に固定設計**する方式だった。この方式には構造的な限界がある。

- 検索回数を「良さそうな数」まで人力で継ぎ足すたびに、その数字が正しい根拠を持たない（5→8→11→14→17回、と際限なく増やせてしまう）。
- 候補を並列で数十件投げるとタイムアウト・接続エラーで破綻する（実測: 30並列でタイムアウト）。
- 「もっと深掘りできないか」を試すたびに新しい価値が見つかり続けるが、これは天井を検出できているのではなく、**ほぼどんな追加クエリでも何かしら価値のある情報が見つかる**ことの裏返りにすぎない。
- 事前に固定したカテゴリ（例: 第三者承継・農地・雇用・補助金の4つ）の中でどれだけ検索回数を増やしても、**設計者が最初から思いつかなかったカテゴリ**（収支シミュレーション・地域差・保険制度など）は原理的に見つからない。これはこのプロダクトの核心価値（ユーザーが思いつかない選択肢を見つけること）そのものを損なう欠陥だった。

一方、`Responses API` の `web_search` ツール（`gpt-5.1`）を1回呼び出すだけで、上記の17回オーケストレーションより包括的な結果が実測で得られた。これはChatGPT等が使う「モデル自身が必要な分だけ反復的に検索するエージェント型」の仕組みであり、検索回数の設計をアプリ側の人力から**モデル自身の判断**へ移す。

## 2. 新設計の要点

1. **検索回数を固定パイプラインで設計しない。** `Responses API` + `web_search` ツールに一任し、1回のAPI呼び出し内で何回検索するかはモデルに委ねる。
2. **「深掘り」は固定段階ではなく、会話の継続（マルチターン）で実現する。** 人間が調査を深める際の「もっと詳しく」「この観点は？」という継続確認と同じ形を踏襲する。
3. **深掘りの「やめどき」は、アプリ側のヒューリスティック（出典数のカウント等）ではなく、モデル自身の構造化された自己判定で決める。** 検索ターンと自己判定ターンを別呼び出しに分離する（4章）。

## 3. アーキテクチャ

### 3.1 検索担当（Pass1相当、`lib/researchAgent.ts`）

- `client.responses.create({ model: "openai/gpt-5.1", tools: [{ type: "web_search" }], ... })` を使用（実際のモデルIDは `ORCAROUTER_AGENTIC_MODEL` で変更可）。
- 初回ターン: `prompts/research_facts.md`（ベースライン事実＋代替ルート探索、`goal.type`別の着眼点）をそのまま `instructions` として渡し、`input` にユーザー入力（`profile`/`goal`のJSON）を渡す。1回で足りない場合、モデルが内部で複数回 `web_search_call` を実行する。
- 追加ターン（深掘り）: `previous_response_id` で会話を継続し、自己判定ターン（4章）が返す不足カテゴリをそのまま次の検索指示にする。

### 3.2 統合先（Pass2相当）との関係 ― 検証済み・2段階構成を維持

現行は「Pass1(検索・軽量facts) → Pass2(検索なし・ResearchResultフルJSON生成)」の2段階。`Responses API` の `web_search` ツールと `text.format`（構造化出力）を併用すれば1本の呼び出しに統合できないか実際に検証した。

**検証結果（2026-08-15、`gpt-5.1`）**: `web_search` ツールと `researchResultSchema` の `text.format` を同時に指定し、`research_system.md` の方針でフルJSONを直接生成させたところ、

- **所要時間 2073秒（約34.5分）**。Vercelの `maxDuration` は言うに及ばず、同期リクエストとしておよそ実用に耐えない。
- **`web_search_call` 回数は0回**。スキーマ検証は通り `sources` も3件生成されたが、実際には一切検索せず一般知識だけで出典らしきものを作った可能性が高い（＝グラウンディングの意味がない）。大きな構造化出力スキーマを同時に満たそうとすると、モデルが検索よりスキーマ充足を優先してしまう懸念がある。

→ **結論: 統合しない。2段階構成を維持する。** 検索担当（`lib/researchAgent.ts`）の出力は軽量な `facts`/`sources`（`MergedFactFinding`、`FactFindingResponse`と構造的に互換）とし、`prompts/research_system.md` によるPass2（検索なし、既存のまま）でJSONを組み立てる。

この「大きな構造化スキーマ＋検索ツールの同居で検索が阻害される」問題は、`lib/researchAgent.ts` 内部の自己判定ターン設計にも直接影響した（4章）。

### 3.3 旧`lib/researchOrchestrator.ts`の扱い

削除済み。3段階の固定オーケストレーション（候補生成／個別グラウンディング／深掘り）とそれに付随する `prompts/research_candidates.md` / `prompts/research_grounding.md` / `types/researchCandidates.ts` を削除した。`prompts/research_facts.md` の内容（`goal.type`別の着眼点等）は変更せず、新方式の初回ターンの `instructions` としてそのまま引き継いでいる。

## 4. 深掘りの「やめどき」— 検索ターン／自己判定ターン分離設計

### 4.1 設計

固定回数を人力で決め打ちしないための停止判定方式。1サイクルは以下の2ターンで構成される（`lib/OrcaRouterClient.ts` の `requestAgenticSearchTurn` / `requestAgenticJudgmentTurn`）。

1. **検索ターン**（`web_search`ツールあり、構造化出力なし）を実行。
2. 直後に**自己判定ターン**（ツールなし、構造化出力 `{sufficient, missing_categories, reasoning}` のみ）を `previous_response_id` で連結して実行。
3. `sufficient: true` なら停止。`false` なら `missing_categories` の内容をそのまま次の検索ターンの指示文にして1に戻る。
4. サイクル数の上限（`MAX_CYCLES = 3`）は「正しい終着点」ではなく、無限ループ・コスト暴走防止の安全弁としてのみ設定する。

**検索ターンと自己判定ターンを別呼び出しに分離しているのは、同じ呼び出しに同居させると3.2節と同じ問題（検索よりスキーマ充足が優先され検索が発火しなくなる）が発生するため。** 小規模な判定スキーマでも同様の問題が起きるかは個別に確認が必要だが、安全側に倒して分離を必須方針とした。

収束後、会話全体（複数ターンの自由記述）を**抽出ターン**（`requestAgenticExtractionTurn`）でPass2が読める `facts`/`sources` 構造（`MergedFactFinding`、facts最大40件）に変換する。

**自己判定の基準（2026-08-15追加）**: 当初の判定基準は「検討すべきカテゴリを網羅したか」だけだった。これでは「制度名・金額は分かるが、実際にそれを使った人の実例が1件も無い」状態でも`sufficient: true`と判定されてしまう欠陥があった（4.3節）。判定プロンプトに **「各カテゴリについて、制度・仕組みの存在だけでなく、それを実際に行った具体的な実例（人物名・地域名・団体名など固有名詞付き）が最低1件含まれているか」** を追加基準として明記し、実例が無いカテゴリは`missing_categories`に含めるよう指示している（`lib/OrcaRouterClient.ts` `requestAgenticJudgmentTurn`）。

### 4.2 検証結果（実測）

- **「新規distinct出典数の増分」は検索回数と相関しない。** 検索を行っても新規性がゼロのターンが実測で複数回確認された（同じ既知カテゴリを言い換えて再検索するだけのケース）。検索回数を深さの指標にするのは誤り。
- **モデル自身の自己判定（`missing_categories`の件数）は先行指標として機能する。** 判定ターンの検索回数は実測で毎回0回（分離設計が機能）。
- **モデルは「残りは個人情報でありWeb検索では解決できない」ことを正しく認識できるケースがある。** 検索0回のまま`missing_categories`が0に収束した例で、モデル自身が「年齢・家族構成・ローン残高等はあなたとの対話で埋めるべき」と理由を明示した（正しい判断）。
- **一方、検索0回のまま`missing_categories`が変化せず停滞し、上限サイクルに達するケースもある**（TOBE PoC 10回中1回）。これは4.1の安全弁が実際に機能した例であり、この場合はその時点までのfactsでPass2に進む（情報が薄い出力になるリスクはあるが、無限ループ・暴走コストにはならない）。

### 4.3 自己判定の欠陥（発見・修正済み）

初期の判定基準（カテゴリ網羅のみ）で収束させた結果を実際に検証したところ、**11件の出典を集めていたにもかかわらず、「実際に誰かがそれをやった」という具体的な実例が1件も含まれていなかった**（制度名・金額の一般論のみ）。加えて出典の中に文脈が確認できない不審なドメインが1件混入していた。カテゴリの自己申告だけでは、この種の「広さはあるが実例が無い」欠落を検出できないことが実測で分かった。

4.2節の基準（実例の有無）を追加した後、同一テーマ（いちご農園）で再実行したところ、**具体的な実例（人物名・地域名付き）が0件→5件に増加**した（第三者承継の実例1件を含む）。検索回数を直接の目標にせず、判定基準の質を上げることで、必要な深掘りが自然に発生することを確認した。

## 6. 実装で追加発覚した問題（Pass2側）

TOBE PoC（Pass1→抽出→実際のPass2まで通した検証）で、検索回数とは別の重大な欠陥が見つかり、合わせて修正した。

### 6.1 Pass2のsourceIndex偽装配分バグ

Pass1が検索3回・facts20件・sources18件という豊富な結果を返しても、Pass2が生成する最終`ResearchResult`では**3本の`targetPaths`が全て同じ1つの`sourceIndex`を参照**しており、実質的な出典の裏付けが1件分しかない状態だった。原因は `prompts/research_system.md` のサンプルJSONが全箇所 `"sourceIndex": 1` になっており、モデルがそのパターンをそのまま模倣していたためと推定される。

**修正**: サンプルJSON内の`sourceIndex`値を箇所ごとに変え（`1`だけを使い回さない）、「3本のパスが異なる手段を扱う場合はそれぞれ異なる情報源を選ぶこと」「`researchedSources`を幅広く使うこと」を明記した。修正後、同じPass1結果に対する再実行でdistinctな`sourceIndex`使用数が1→6に増加したことを確認。

### 6.2 sourceIndexの範囲外参照バグ（6.1の修正で新規発生）

6.1の修正直後、今度は`sources`配列の長さ（4件）を超える`sourceIndex`（5・6・7）を参照する出力が発生した。`sourceIndexSchema`（`z.number().int().min(1)`）には上限チェックがなく、この不整合はスキーマ検証を素通りしていた。

**修正**: `types/research.ts`の`researchResultSchema`に`superRefine`を追加し、全ての`sourceIndex`系フィールド（`currentPath`/`targetPaths[]`/`checks[]`/`rateSourceIndex`/`summary`配下の各fact/`leadSourceIndexes`）が`sources.length`以内であることを横断検証するようにした。これにより既存のPass2リトライ機構（`route.ts`の`retryHint`）がこのエラーメッセージを使って自動的に再生成を促せる。

## 7. 検索回数の実測値（製品スペックとしての合意事項）

### 7.1 「検索回数」の単位に関する訂正（重要）

当初、`output`配列内の`web_search_call`アイテムの**個数**を「検索回数」として報告していた（10回の実行で2〜5回、平均約3回）。しかし実際に`web_search_call`アイテムの中身（`action.queries`）を確認したところ、**1アイテムが平均4件の実クエリを内包している**ことが判明した（複数回の実測で一貫して4件）。

さらに、レスポンスオブジェクトには `tool_usage.web_search.num_requests` という公式フィールドが存在し、これが実際に実行された検索クエリ数を直接示すことが分かった（`action.queries.length`の手動集計と一致）。**したがって「検索回数」は`web_search_call`アイテム数ではなく、`num_requests`の合計で数えるべき。**

この訂正を踏まえた実測（いちご農園、3サイクルで収束）:

| サイクル | `num_requests` | 新規distinct出典URL |
|---|---|---|
| 1 | 4 | 0 |
| 2 | 8 | 7 |
| 3 | 4 | 4 |
| **合計** | **16** | **11** |

**Pass1の実クエリ数（`num_requests`ベース）: 約8〜20回、平均約12回**（旧・イベント数ベースの「2〜5回」に対応する範囲を4倍したもの）。

### 7.2 情報量の自然さ検証

「少ない検索回数でこの情報量は不自然ではないか」という懸念に対し、上記の実測データで検証した。**distinct出典数(11) ÷ 実クエリ数(16) = 0.69**。1クエリあたり平均1件未満しか新規出典を生んでおらず、実際にサイクル1では4クエリで新規出典0件だった。検索の割に得られる情報が少なめであり、「効率が良すぎて不自然」という状態ではないことを確認した。

なお、1クエリあたり実際に何ページを読んでいるか（SERP件数・閲覧ページ数）はAPIのレスポンスに一切露出しておらず、確認不可能。

### 7.3 最終合意値

「人生設計全体」の検索回数はPass1のみで発生し、以下を加算・減算したもの:
- テーマ入力（`app/page.tsx`のS01画面）: **0回**（ハードコードされた3つのサジェストチップ、または自由記述。AI・検索は介在しない）
- ヒアリング（`/api/interview`）: **0回**（検索なしの動的質問生成）
- Pass2（詳細生成、`requestResearchCompletion`）: **0回**（3.2節の検証により意図的に検索なし）

→ **人生設計全体の実クエリ数 = 約8〜20回、平均約12回。**

### 7.4 自己判定基準の追加（4.3節）による影響

当初の自己判定基準（カテゴリ網羅のみ）で「十分」と判定された結果を検証したところ、11件の出典があっても具体的な実例（人物名・地域名付き）が1件も含まれていなかった。4.3節の基準追加後、同一テーマで実例が0件→5件に増加した。この際の検索回数（`num_requests`）は個別計測していないが、所要時間は206〜227秒台で従来と同水準であり、「回数を無理に増やす」のではなく「必要な分だけ自然に増える」設計の狙い通りに機能している。

## 9. 停止条件の設計（TOBE、未実装）

要求水準: 人生設計の意思決定に足る調査量として、実クエリ数（`num_requests`）で100回相当を目安とする。ただしこの数はアプリ側が強制する目標値ではなく、9.2の判定基準を満たした結果として到達する値とする。

### 9.1 停止条件（3種類、優先度順）

`runAgenticFactFindingStep`のサイクルは、以下いずれかに該当した時点で終了し、抽出ターン＋Pass2へ進む。

| # | 条件 | 意味 |
|---|---|---|
| 1 | 自己判定ターンが `sufficient: true` を返す | 9.2の基準を全て満たした（正常終了） |
| 2 | 直近2サイクル連続で新規実クエリ数（`search.numRequests`）が0 | これ以上検索しても新しい情報が得られないと客観的に判断できる状態（打ち切り） |
| 3 | サイクル数が `STEP_MAX_CYCLES`（暫定30）に到達 | コスト・レイテンシの安全弁（最終手段） |

条件2は、100回という目標回数を人力で決め打ちする代わりに、**「そのリクエスト固有の実測」に基づいて過不足を判定する**ための機構である。検索回数そのものを目標にしないという設計原則（2章）を条件1・3と同様に維持する。

### 9.2 自己判定の基準

判定ターン（`requestAgenticJudgmentTurn`）は、以下6項目の充足を確認し、いずれか1つでも未達なら`missing_categories`に具体的な不足点を列挙する。

1. 検討すべき重要カテゴリの網羅
2. カテゴリごとに条件の異なる複数の実例（1件のみは不可、成功例・苦戦例など）
3. 重要な数値の複数情報源による裏付け
4. 3箇所以上の具体的な地域比較
5. 楽観・標準・悲観の複数シナリオでの収支
6. 失敗・撤退リスクの定量化と、3〜5年以上の長期見通し

### 9.3 状態管理の拡張

`AgenticStepState`（`types/agenticSearch.ts`）に `consecutiveZeroNewQueries: number` を追加する。`runAgenticFactFindingStep`は毎サイクル、`search.numRequests === 0` ならこの値をインクリメント、1以上ならリセットし、`consecutiveZeroNewQueries >= 2` で9.1条件2による終了とする。

### 9.4 Pass1/Pass2の役割分担

9.2の基準のうち、Web検索で直接見つかる性質のもの（2・3・4、実例・数値・地域比較）はPass1が担当する。基準5（複数シナリオ収支）・6の一部（長期見通しの試算）は、個別の事実というより**既存のfactsからの統合・計算を要する情報**であり、Pass1の検索では原理的に満たせない場合がある。この場合、9.1条件2で停止した時点の`missing_categories`の残り項目を、抽出ターンの出力に含めて Pass2 の生成指示（`buildResearchPrompt`）へ引き継ぎ、Pass2側で試算・統合させる設計とする。
