# API利用設計（モデル・コスト）

対象範囲: LLM（OrcaRouter経由）の呼び出しコストのみ。`handoff`（エージェント・専門家への相談リンク）や`paywall`（追加リサーチの課金）は`disabled`のモック実装であり本ドキュメントの対象外（[components/result/ActionSection.tsx](../components/result/ActionSection.tsx)）。性能グレード（松竹梅＝モデル選択・リサーチ構成）とは独立した別軸の未実装機能であり、モデルを松にしても自動的に実装されるものではない。

前提: LLM呼び出しは全て OrcaRouter（OpenAI互換ルーター、`baseURL: https://api.orcarouter.ai/v1`）経由。料金は **OrcaRouterが接続先モデルのOpenAI公式価格に準拠している前提**で試算する（OrcaRouter独自の上乗せ有無は未確認）。モデル価格は `GET /v1/models`（OrcaRouter）のレスポンスから取得（2026-08-14）。

## 1. 利用モデルと切り替え方法

| 用途 | 呼び出し箇所 | 環境変数 | 現在値 | Web Search |
|---|---|---|---|---|
| ヒアリング質問生成 | `/api/interview` | `ORCAROUTER_MODEL` | `openai/gpt-4o-mini` | なし |
| 基礎調査（Pass1） | `/api/research` 内 | `ORCAROUTER_FACT_MODEL` | `openai/gpt-4o-mini-search-preview` | あり |
| 詳細生成（Pass2） | `/api/research` 内 | `ORCAROUTER_MODEL` | `openai/gpt-4o-mini` | なし（search系モデルの出力上限〈実測1,000〜1,500トークン〉を回避するため意図的に無効） |

**切り替え方法**: Vercel Environment Variables の `ORCAROUTER_MODEL` / `ORCAROUTER_FACT_MODEL` を書き換えて再デプロイする（コード変更不要、`lib/OrcaRouterClient.ts` が実行時に読む）。`ORCAROUTER_FACT_MODEL` を空にするとPass1自体をスキップする設計。

## 2. リサーチ設計（Pass1 / Pass2の役割分担）

- **Pass1**: Web検索を行い、事実・相場・制度情報を収集する担当。検索を行うのはこのステップのみ。
- **Pass2**（`prompts/research_system.md`）: Pass1が集めた事実と一般知識のみを根拠に、比較結果（`ResearchResult`）を構造化生成する担当。Pass2自身は検索しない。

Pass1の実装は `mode`（`eco` / `normal`）によって異なる（[app/api/research/route.ts](../app/api/research/route.ts) の `runFactFindingBestEffort`）。

### mode: "eco" — 単一呼び出し

`prompts/research_facts.md` を1回のAPI呼び出しに渡し、ベースラインの事実と代替ルートの探索をまとめて任せる。低コストだがカバレッジは不安定（4章）。

### mode: "normal" — 3段階オーケストレーション（`lib/researchOrchestrator.ts`）

1. **候補生成**（`prompts/research_candidates.md`、Web検索なし・1回）: `goal.type`/`goal.description` から、素朴なフルコース以外の代替ルート候補を最大6件、一般知識のみで発想する。`goal.type` による着眼点の違い:
   - `independence`: 第三者承継・事業承継／資産を借りる・間借りする仕組み／雇われながら学べる制度／自治体・国の補助金
   - `career_change`: 未経験者向け特別選考・ポテンシャル採用／職業訓練校・スクールと教育訓練給付金／副業・フリーランスでの実績づくり／人材紹介・紹介予定派遣
2. **個別グラウンディング**（`prompts/research_grounding.md`、Web検索あり・並列）: ベースライン1件＋候補ごとに1件、狭い質問で実在を検索確認する。出典が付かない候補はそのまま脱落させる（無理に埋めない）。
3. **深掘り**（同上、Web検索あり・並列・最大3件）: ステージ2で出典が付いた候補のうち、情報源が多い順に上位3件について、具体的な金額・要件・申請の流れを追加で調べる。

## 3. 設計上の各ステージの検証根拠

以下は各ステージの設計判断を裏付けた実測（`gpt-4o-mini-search-preview`、2026-08-15）。

- **単一呼び出し（mode: eco）の限界**: 現行の単一呼び出しを4回試行したところ、5対象（ベースライン＋代替ルート4カテゴリ相当）すべてに実在の出典が付いた回は0回。ベースライン経済性の話に偏る回、代替ルートに触れても出典なしの回があった。
- **カテゴリの固定化は不可**: 「第三者承継・借地・雇用・補助金」を全テーマ共通で固定していたところ、`career_change`テーマ（「デザイナーに転職したい」）で4カテゴリ中2つが空振り・こじつけになった。`goal.type`別に着眼点を出し分けることで解消（テーマ「デザイナーに転職したい」で4カテゴリ全てに実在サービスを発見）。
- **狭い質問は検索を確実に発火させ、広い質問は発火しない**: 「〜はありますか？」という個別の狭い質問は毎回web検索が発火し実在の出典が付いた。一方「代替ルートを最大8件挙げて」のような列挙型の質問は、指示で「検索で確認できたものだけ」と制約しても検索が発火せず、出典0件のまま一般知識で埋めた回答が返った。→ **候補生成は検索なしの列挙で概要を出し、実在確認は個別の狭い質問に分けて検索させる**、という2段階構成の根拠。
- **無制約の列挙は6〜8件を超えると劣化する**: 個数上限を設けずに代替ルートを列挙させると、上位5〜8件までは有効だが、それ以降は同一項目の言い換え・重複や、ゴールと無関係な項目（SNS運用・ブログ運営等）に劣化した。→ **候補生成の上限を6件**とした根拠。
- **深掘りは対象によって価値が非対称**: 「制度の具体的な金額・要件」を深掘りすると新規の実在情報が得られた（例: 継承奨励金の月額交付額・年齢要件・所得要件などをステージ2の一次発見から追加取得）。一方「就農後の収益推移の実例」「承継特有のリスク」を深掘りしても出典は付かず、一般知識の域を出なかった。→ **深掘りは「具体的な金額・要件・申請の流れ」に絞る**、それ以外（収益推移・リスク一般論）はPass2側の一般知識・不確実性の明記に委ねる、という設計根拠。

## 4. トークン数の設計根拠（Pass2、スキーマ構造に基づく実測内訳）

`prompts/research_system.md` と `types/research.ts`（`researchResultSchema`）を `tiktoken`（`o200k_base`）で計測。Pass2に渡す入力（システムプロンプト＋JSON Schema＋ヒアリング回答＋Pass1の事実）とスキーマが要求する出力構造はモデルを変えても同一のため、**入出力トークン数の土台は全グレード共通**として扱う。

### 入力（リクエストごとに固定される部分）

| 構成要素 | トークン数 | 備考 |
|---|---|---|
| `research_system.md`（システムプロンプト本文） | 5,758 | 固定 |
| `researchResultSchema`（JSON Schema定義、`response_format`で毎回送信） | 2,349 | 固定 |
| ヒアリング回答・プロフィール・Pass1の事実 | 約120〜300（mode: eco）／数百〜1,000超（mode: normal、Pass1のfacts量に応じて増加） | 変動 |
| **合計** | **約8,200〜8,300（mode: eco基準）** | 実測値8,226と整合。固定分8,107はプロンプトキャッシュ対象（実測でも7,040トークンがキャッシュ扱い） |

### 出力（生成されたJSONの構造別トークン数）

| フィールド | トークン数 | 出力全体比 | スキーマ上の制約（`types/research.ts`） |
|---|---|---|---|
| `summary` | 167 | 4% | 固定4項目（fitScore/availableFunds/survivalPeriod/relevantExperience） |
| `currentPath` | 682 | 16% | 「今のまま」1件、`yearlyScenes`(y1/y3/y5)必須 |
| `targetPaths`×3 | 3,164 | **72%** | `targetPaths.length(3)` で必ず3件固定。1件あたり約1,000〜1,100トークン |
| `checks` | 138 | 3% | `min(3).max(8)` |
| `sources` | 212 | 5% | 可変 |
| **合計** | **約4,400〜5,300** | | `targetPaths.length(3)`固定により出力の7割超を`targetPaths`が占める |

## 5. 性能グレード比較（松竹梅）

| グレード | 構成 | Pass1 API呼び出し回数（想定） | うちWeb Search回数（想定） | ヒアリング / Pass1 / Pass2 | 1回あたり | 現状比 |
|---|---|---|---|---|---|---|
| 🍃 梅（エコ性能・現行） | mode: eco（単一呼び出し） | **1回** | **1回**（実測は0〜1回、不安定。3章） | gpt-4o-mini / gpt-4o-mini-search-preview / gpt-4o-mini | **約$0.03（≒4.5円）** | 1x |
| 🎋 竹（推奨性能） | mode: normal（3段階オーケストレーション） | **11回**（候補生成1＋ステージ2最大7＋ステージ3最大3、実測10〜11回） | **9〜10回**（ステージ2・3、実測平均9.5回） | gpt-5.1 / gpt-5-search-api / gpt-5.1 | **約$0.34（≒51円）** | 約11x |
| 🌲 松（最高性能） | mode: normal ＋ Pass2を最上位モデルに | 竹と同じ（**11回**） | 竹と同じ（**9〜10回**） | gpt-5.1 / gpt-5-search-api / gpt-5.5-pro | **約$1.5〜$2.5（≒225〜375円）** | 約50〜83x |

竹・松のPass1呼び出し回数の内訳（`lib/researchOrchestrator.ts`）: 候補生成1回（検索なし）＋ステージ2（ベースライン1回＋候補最大6件＝最大7回、検索あり）＋ステージ3（深掘り最大3回、検索あり）＝**最大11回**。候補6件のうち実在確認できる（＝深掘り対象になる）のは実測で2〜3件のため、実際に発火するAPI呼び出しは10〜11回、うちWeb Searchは9〜10回（候補生成のみ検索なし）。

| 基礎調査（トークン分＋Web Search1回） | 961 | 763 | $0.0256 |

### 🎋 竹（推奨性能）

`lib/researchOrchestrator.ts` の3段階オーケストレーションを実際に2回実行し、実測。

| 実行 | API呼び出し回数 | うちWeb Search | prompt tokens | completion tokens | 所要時間 |
|---|---|---|---|---|---|
| 1回目 | 10 | 9 | 7,061 | 2,610 | 16.7秒 |
| 2回目 | 11 | 10 | 7,704 | 2,799 | 14.8秒 |

候補生成6件のうち、実在の出典が付いてグラウンディングに成功したのは各回2〜3件（深掘り対象もその件数）。ヒアリング・Pass2は`gpt-5.1`（$1.25/$10 per M）、Pass1は`gpt-5-search-api`（同単価）で試算。

| 内訳 | 料金 |
|---|---|
| ヒアリング生成 | $0.0044 |
| Pass1（トークン分＋Web Search、実測平均） | 約$0.27 |
| Pass2（入力8,300×$1.25/1M ＋ 出力5,300×$10/1M） | $0.063 |
| **合計** | **約$0.34** |

### 🌲 松（最高性能）

Pass2のみカタログ最上位の推論モデル `gpt-5.5-pro`（$30/$180 per Mトークン）に置き換える。ヒアリング・Pass1は竹と同じ（約$0.27+$0.0044）。

Pass2: 入力8,300×$30/1M=$0.249、出力5,300×$180/1M=$0.954 → **$1.20**（可視出力のみの下限値）。
推論系モデルは可視出力の裏で「隠れ思考トークン」も課金されるケースがあるため、可視出力の2倍を仮置きした上限値も併記: 出力10,600×$180/1M=$1.908 → Pass2で**$2.16**（この倍率は未実測の目安）。

| シナリオ | 合計 |
|---|---|
| 下限（可視出力のみ） | 約$0.27+$1.20 ≒ **$1.5** |
| 上限（隠れ思考トークン込み） | 約$0.27+$2.16 ≒ **$2.4** |

**運用上の注意**: 実運用投入前に、応答時間（推論モデルは数分単位になりうる）・現行の `maxDuration=120`（Vercel）との整合・JSON Schema出力の安定性を実機で検証すること。オーケストレーション自体（竹の構成）は実測15〜17秒で完走しており、Pass2と合わせても`maxDuration=120`に収まる。
